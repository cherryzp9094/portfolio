Keystore 기반 로그인 정보 암호화

데이터 암호화 마이그레이션 · 2025.08 · 기여도 100%

상황로그인 비밀번호가 기기에 평문으로 저장되는 문제를 직접 찾아 주도적으로 개선했습니다. SharedPreferences를 DataStore로 옮기려 했지만 DataStore도 기본 암호화를 제공하지 않아 저장소 자체에 암호화를 넣어야 했습니다.

해결DataStore를 감싼 보안 저장소를 만들어, 값을 저장할 때 암호화하고 읽을 때 복호화하도록 했습니다. 키는 Android Keystore에서 AES-GCM으로 생성·관리해 앱 밖으로 꺼낼 수 없게 했습니다. 비밀번호를 쓰던 화면 7곳(로그인, 회원가입, 스플래시, 회원정보 수정 등)을 이 저장소로 직접 옮겼고, 이미 배포된 앱의 평문 데이터는 앱 시작 시 암호화 저장소로 옮긴 뒤 삭제해 강제 업데이트 없이 전환했습니다.

결과

  • 로그인 실패 0건

위젯 Glance 재구축

Compose 위젯 리뉴얼 · 2024.11 ~ 12 · 기여도 100%

팀 구성 · Android 1

상황RemoteViews 기반 레거시 위젯이 유지보수가 어려웠고, 앱과 위젯 사이 데이터가 어긋나 값이 오래된 채로 남는다는 VOC, 고해상도 기기에서 텍스트가 안 읽힌다는 VOC가 들어왔습니다.

해결RemoteViews를 Jetpack Glance로 옮겼습니다. Compose 문법으로 작성하지만 실제로는 RemoteViews로 변환돼 홈 화면에 그려지기 때문에, 일반 Compose와 쓸 수 있는 컴포넌트와 스타일이 다릅니다.

동기화는 WorkManager 주기 작업 + DataStore(Protobuf)로 옮겼습니다. Glance 기본 저장소(Preferences)는 문자열·숫자 같은 단일 값만 담을 수 있어, 예약 목록처럼 구조가 있는 데이터를 스키마로 정의해 저장했습니다.

절전 모드는 VOC로 들어온 것이 아니라 작업 중 직접 조사해 파악한 부분입니다. 절전 모드에서는 백그라운드 작업이 제한돼 위젯이 데이터를 받아 오지 못했습니다. 배터리 최적화 예외 같은 민감 권한으로 강제할 수도 있었지만 스토어 심사에서 리젝 사유가 될 수 있어, 동기화할 때 절전 모드를 확인하고 해제를 안내하는 UI로 풀었습니다.

텍스트는 앱 실행 시 해상도·글자 크기를 저장해 렌더링 때 조정했습니다. 이 프로젝트에서 LeakCanary를 도입해 Crashlytics·ANR이 못 잡던 메모리 누수를 잡기 시작했고, 이후 실제 누수 수정으로 이어졌습니다.

결과
  • 데이터 불일치·텍스트 VOC 해소
  • 절전 모드 해제 안내 UI 제공
  • 운영 기간 위젯 관련 크래시 0건(Crashlytics)
  • LeakCanary는 이후 팀 빌드 옵션으로 정착

회고텍스트 크기 조정은 앱을 한 번 실행해야 반영됩니다. 위젯 단독으로 갱신할 방법을 못 찾았고, 그 한계는 그대로 남았습니다.

  • Glance
  • WorkManager
  • DataStore(Protobuf)
  • LeakCanary

레거시 아키텍처 Kotlin·Compose 전환

레거시 아키텍처 전환 · 2021.11 ~ 2026.05 · 재직 기간 동안 단계적으로 진행 · 기여도 30%

팀 구성 · Android 3

상황Java 71%의 MVC + AsyncTask 레거시. 앱마다 레포가 나뉘어 있어 공통 코드가 중복됐습니다. 서비스는 계속 굴러가야 했으므로 한 번에 갈아엎는 선택지는 없었습니다.

해결서비스를 멈추지 않으려고 4단계로 나눠 순차 전환했습니다.

단계 전환 판단
1 Java → Kotlin 신규는 Kotlin으로 시작, 레거시는 영향도가 낮은 파일부터 전환
2 멀티레포 → 모노레포 Presentation / Network / Common 3-Layer 멀티모듈
3 MVVM → MVI Compose·MVI 스터디를 열어 구성원과 함께 학습하고 코드 컨벤션 정리
4 XML → Compose 디자인 시스템부터 만들고, 신규·개편 화면부터 단계적으로 전환

아키텍처를 옮기고 나니 다음 병목은 빌드였습니다. 구버전 AGP에 병렬 빌드와 캐시가 꺼져 있어 최대 8분이 걸렸습니다. VersionCatalog로 모듈 간 버전을 맞추고, AGP·Gradle 최신화, Hilt의 kapt → KSP 전환과 Kotlin 2.0(K2) 업그레이드, 병렬 빌드·캐시 활성화로 빌드 시간을 줄였습니다.

결과
  • Java → Kotlin 28.8% → 99.2%
  • 앱별 레포를 모노레포로 통합 → 3개 앱 단일 구조 운영
  • 빌드 최대 8분 → 3분

AI 기반 ViewModel 테스트 자동 생성 파이프라인 설계

테스트 자동화 · 2025.07 ~ 2026.02 · 기여도 100%

상황기존 자동 생성 스킬이 LINE 커버리지를 20.6%까지 올려둔 상태였는데, 생성된 테스트가 실패하면 결국 사람이 붙어야 해서 그 위로 올라가지 못하고 있었습니다.

자동화에 앞서 테스트를 어떤 모양으로 쓸지부터 정했습니다. Given-When-Then 패턴을 표준으로 잡아 요구사항 단위로 시나리오를 설계했고, 대상은 ViewModel의 비즈니스 로직으로 한정했고(JUnit5 · MockK · Turbine), UI 테스트는 이 파이프라인의 범위에 넣지 않았습니다. 형식이 정해져 있어야 자동 생성이 의미를 갖는다고 봤기 때문입니다.

해결생성만으로는 부족하다고 보고, 고치는 단계까지 넣은 5단계 파이프라인을 Claude Code로 설계했습니다.

Planner → Scaffold → Generator → Healer → Coverage
                          ↑          ↓
                          └──────────┘  실패 테스트 자동 진단·수정 루프

핵심은 네 번째 수정 단계(Healer) 입니다. 실패한 테스트를 자동 진단해 고치고 다시 검증 루프를 도는 구조라, 사람 개입 없이 통과 가능한 지점까지 도달합니다.

결과
  • 3,805줄 ViewModel 기준 LINE 20.6% → 83% / BRANCH 6.3% → 52% / METHOD 30% → 88% — 이후 전체 ViewModel에 적용
  • QA 집계 기준 회귀 버그 티켓 50% 감소

세 지표를 함께 보는 이유는 LINE만으로는 분기 미탐지가 가려지기 때문입니다.

회고초기에 relaxed mock을 쓰다 분기를 못 잡는 문제가 있었습니다. MockWebServer + JSON fixture 패턴으로 전환했습니다.

상담봇 RAG 적용·최적화

사내 AI 봇 운영 · 2026.04 ~ 05 · 기여도 100%

상황사내 AI 봇 운영을 맡았습니다. 고객 상담봇은 최상위 모델이 질문마다 지식 베이스 전체를 훑어 답하는 구조라 토큰 소모가 컸고, 가장 높은 요금제를 쓰고도 사용 한도에 걸려 업무 시간 중에 상담이 멈추는 일이 생겼습니다. 자동응답 회수율도 22%에 머물렀습니다. 비용과 품질을 함께 고쳐야 한다고 보고 최적화를 시작했습니다.

해결고객에게 바로 나가는 시스템이라 비대칭 리스크가 있다고 봤고, 개선안을 바로 넣는 대신 측정 인프라부터 만들었습니다. 오답률·회수율·건당 비용 3축을 매일 자동 수집한 뒤, RAG 파이프라인과 토큰 구조를 재설계해 8개 variant를 Shadow A/B로 비교하고 대부분을 기각했습니다.

결과

최종 후보 측정값

  • 건당 비용 ₩2,173 → ₩97 (-96%)
  • 자동응답 회수율 22% → 43%
  • overconfidence 73% → 20%

다만 배포는 중단했습니다. 카나리 배포 직전 지식 베이스를 감사해 보니 고객에게 보여서는 안 되는 데이터가 섞여 있었습니다. 자격 증명 평문 6건(플레이스토어 계정 포함)과 회사 계좌 2건으로, 정규식 1차 필터에 LLM 2차 검증을 붙인 탐지 파이프라인을 직접 만들어 찾아냈습니다. 상담봇이 이 데이터를 답변에 실을 수 있는 상태였기 때문에, 지식 베이스를 사람이 한 번 검수하는 과정이 먼저 필요하다고 판단했습니다.

이 기간 운영에 반영한 것은 최우선 버그 7건 수정과 지식 베이스 카테고리 표준 분류 724건입니다. 파이프라인 개선분은 보안 보고서와 조치 권고를 올리고 봇 검색용 데이터와 사람 검토용 데이터를 분리하는 설계 변경을 제안하는 데서 마무리했습니다.

통합 회원가입 · 2021.11 ~ 2022.03 · 기여도 100%

팀 구성 · Android 1 · iOS 1 · Frontend 1 · Backend 2 · Product Designer 1

상황원장과 직원의 회원가입이 분리돼 있었습니다. VOC·버그 대응으로 주 2~3회 불규칙하게 배포하던 상황이었습니다.

해결회원가입을 통합하고 강제/선택 업데이트를 구현했습니다. 배포 후 백엔드 롤백이 필요한 크리티컬 이슈가 났는데, 네이티브 앱은 심사와 배포를 거쳐야 해서 기민하게 대응하기 어려웠습니다. 그래서 Firebase RemoteConfig 피처 플래그 도입을 제안해 배포 없이 기능을 켜고 끌 수 있게 했고, 불규칙 배포를 정기 배포로 바꿨습니다. 업무 우선순위 제도도 함께 도입했습니다.

결과
  • 통합 회원가입 배포.
  • 이후 장애는 앱 배포 없이 피처 플래그로 기능을 내려 대응할 수 있게 됐고, 이후 큰 프로젝트 배포에서 활용했습니다

회고백엔드는 바로 되돌릴 수 있어도 네이티브 앱은 장애에 기민하게 대응하기 어렵다는 것을 겪었습니다. 정기 배포와 피처 플래그가 왜 필요한지 이때 체감했습니다.

네이버페이 매장결제 연동

네이버 연동 고도화 · 2025.11 ~ 2026.05 · 기여도 100%

Android 1 · iOS 1 · Frontend 1 · Backend 1 · Product Designer 1

상황네이버 헤어샵을 통한 고객 유입을 늘리기 위해 네이버페이 매장결제·예약금·쿠폰·스타일 태그를 앱에 연동하는 프로젝트였습니다. 매장결제는 앱에서 결제를 요청한 뒤 고객이 자기 휴대폰에서 결제를 마칠 때까지 앱이 기다려야 하는 구조라, 그 사이에 결제 결과를 앱이 알 방법이 필요했습니다.

해결서버가 앱으로 결과를 알려주는 방식이 더 낫다고 봤지만 작업 공수가 매우 짧았습니다. 그래서 타임아웃을 두고 일정 주기로 승인 여부를 API로 확인하는 폴링 방식을 먼저 도입하자고 제안해 구현했습니다.

화면은 결제 요청 → 진행 중 → 완료 → 환불까지 전 플로우를 Compose + MVI로 만들었고, 스타일 태그는 카테고리별 복수 선택이 가능한 바텀시트로 구현했습니다. 백엔드 API가 나오기 전에는 로컬 JSON 목 데이터로 통신 케이스를 미리 만들어 개발하고 엣지 케이스를 먼저 공유했습니다. 외부 결제가 섞이면서 달라지는 매출·포인트 계산은 경우별로 백엔드와 규칙을 다시 맞췄습니다.

결과
