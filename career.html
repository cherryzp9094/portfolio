레거시 아키텍처 Kotlin·Compose 전환

레거시 아키텍처 전환 · 2021.11 ~ 2026.05 · 재직 기간 동안 단계적으로 진행 · 기여도 30%

팀 구성 · Android 3

상황Java와 MVC로 구현된 앱이었고 앱마다 레포가 나뉘어 공통 코드가 중복됐습니다. 서비스는 계속 운영돼야 해서 한 번에 전면 개편할 수는 없었습니다.

해결서비스를 멈추지 않도록 3단계로 나눠 차례로 전환했습니다.

단계 전환 판단
1 Java MVC → Kotlin MVVM 신규 코드는 Kotlin과 MVVM으로 작성하고 레거시는 영향도가 낮은 파일부터 전환
2 멀티레포 → 모노레포 + 멀티모듈 B2C까지 3개 앱을 하나의 레포로 합치고 공통 기능은 모듈로 분리해 앱끼리 공유
3 MVVM → MVI, XML → Compose Android 팀원과 스터디로 Compose와 MVI를 함께 익힌 뒤 디자인 시스템의 테마와 공통 컴포넌트를 만들며 신규 화면과 개편 화면부터 전환

아키텍처를 옮긴 뒤에는 앱 빌드가 최대 8분까지 걸려 다음 병목이 됐습니다. 어노테이션 처리는 kapt가 필요한 일부만 남기고 KSP로 전환했고 Kotlin 2.0 K2 컴파일러로 올렸습니다. 여기에 VersionCatalog로 모듈 간 버전을 맞추고 AGP와 Gradle을 최신화하면서 병렬 빌드와 캐시도 켰습니다.

결과
  • Kotlin 비중 99.2%까지 전환
  • AsyncTask 기반 API 호출을 Retrofit과 Coroutine으로 모두 교체
  • 3개 앱을 하나의 모노레포로 통합해 공통 모듈 공유
  • Compose 디자인 시스템의 테마와 공통 컴포넌트를 직접 구축해 화면 전환의 기반으로 사용
  • Activity 기준 약 85%를 Compose로 전환
  • 빌드 시간 최대 8분 → 3분 단축

Compose·MVI 성능 최적화

고객 목록 개선 · 2024.07 ~ 11 · 기여도 100%

팀 구성 · Android 1 · iOS 1 · Frontend 1 · Backend 1 · Product Designer 1

상황고객 목록에 필터와 그룹 기능을 더하면서 항목 추가나 입력 필드 변경처럼 일부 값만 바뀌어도 리스트 전체가 리컴포지션되어 화면이 버벅이는 현상이 발생했습니다. 목록을 스크롤할 때도 끊김이 있었습니다.

해결Layout Inspector로 확인한 원인은 세 가지였습니다. 목록 항목을 위치로만 구분해 항목 하나를 추가하거나 지우면 뒤쪽 항목이 모두 다시 그려졌습니다. Compose는 List나 디자인 시스템 컴포넌트의 색상 정의처럼 안정성을 판단할 수 없는 타입을 받으면 비교를 건너뛰지 못합니다. 그래서 텍스트 필드 값만 바뀌어도 내용이 같은 리스트와 공통 컴포넌트까지 리컴포지션됐습니다. 맨 위로 버튼과 다음 페이지 요청 조건은 스크롤 위치를 그대로 읽어 스크롤하는 동안 계속 리컴포지션됐습니다.

목록 항목에는 고유한 key를 주어 바뀐 항목만 다시 그려지게 했습니다. UI 모델의 리스트는 kotlinx persistent 컬렉션으로 바꾸고 디자인 시스템 컴포넌트의 색상과 모양 정의에는 @Stable을 붙여 바뀌지 않은 부분은 건너뛰게 했습니다. 스크롤 위치에 따라 바뀌는 값은 derivedStateOf로 감싸 결과가 바뀔 때만 다시 그려지게 했습니다. 실시간 검색은 debounce로 불필요한 API 호출을 줄였습니다.

이후 추가 개선을 위해 Compose 심화 스터디를 주관하고 스터디에서 다룬 최적화를 다른 화면에도 적용했습니다.

결과
  • 목록 스크롤 끊김 해소
  • Layout Inspector 기준 값이 바뀐 컴포넌트만 리컴포지션되도록 개선
  • 디자인 시스템 공통 컴포넌트를 안정적인 타입으로 정리해 이를 쓰는 화면에 같은 최적화가 기본 적용
  • 실시간 검색의 불필요한 API 호출 감소

위젯 Glance 재구축

Compose 위젯 리뉴얼 · 2024.11 ~ 12 · 기여도 100%

팀 구성 · Android 1

상황기존 위젯은 XML과 RemoteViews로 화면을 그리고 데이터는 SQLite에 저장하는 구조라 유지보수가 어려웠습니다. 앱과 위젯의 데이터가 어긋난다는 VOC와 고해상도 기기에서 텍스트가 안 읽힌다는 VOC도 들어왔습니다.

해결위젯을 Compose 기반인 Jetpack Glance로 다시 만들고 동기화는 SQLite 대신 WorkManager 주기 작업과 Proto DataStore로 옮겼습니다. Glance 기본 저장소인 Preferences는 키마다 기본 타입 값만 담을 수 있어 예약 목록은 스키마로 정의해 Proto DataStore에 저장했습니다. 텍스트는 앱 실행 시 해상도와 글자 크기를 저장해 두고 위젯을 그릴 때 조정했습니다. 이 작업에서 LeakCanary도 도입해 Crashlytics로는 못 잡던 메모리 누수를 찾아 고쳤습니다.

배포 후에도 데이터를 간헐적으로 불러오지 못한다는 VOC가 남아 직접 조사했고 절전 모드에서 백그라운드 작업이 제한되는 것이 원인이었습니다. 배터리 최적화 예외 같은 민감 권한은 스토어 심사에서 반려 사유가 될 수 있어 동기화할 때 절전 모드를 확인하고 해제를 안내하는 UI를 띄웠습니다.

결과
  • 데이터 불일치와 텍스트 VOC 해소
  • 절전 모드 안내 후 간헐적 로드 실패 VOC 해소
  • XML과 SQLite 기반 레거시 위젯 코드 제거
  • Crashlytics 기준 운영 기간 위젯 관련 크래시 0건
  • LeakCanary를 팀 빌드 옵션으로 정착

회고텍스트 크기 조정은 앱을 한 번 실행해야 반영됩니다. 위젯 단독으로 갱신할 방법은 찾지 못해 한계로 남았습니다.

  • Glance
  • WorkManager
  • Proto DataStore

Keystore 기반 로그인 정보 암호화

데이터 암호화 마이그레이션 · 2025.08 · 기여도 100%

상황로그인 비밀번호가 기기에 평문으로 저장되는 문제를 직접 찾았습니다. EncryptedSharedPreferences는 deprecated된 상태였고 DataStore도 기본 암호화를 제공하지 않아 저장소 자체에 암호화를 넣어야 했습니다.

해결DataStore를 감싼 보안 저장소를 만들어 값을 저장할 때 암호화하고 읽을 때 복호화하도록 했습니다. 키는 Android Keystore에서 AES-GCM으로 생성해 앱 밖으로 꺼낼 수 없게 했습니다. 로그인, 회원가입, 스플래시, 회원정보 수정 등 비밀번호를 쓰던 화면 7곳을 이 저장소로 직접 옮겼고 이미 배포된 앱의 평문 데이터는 앱 시작 시 암호화 저장소로 옮긴 뒤 삭제했습니다.

결과

  • 기존 사용자는 다시 로그인하지 않고 앱 업데이트만으로 전환

AI 기반 ViewModel 테스트 자동 생성 파이프라인 설계

테스트 자동화 · 2026.02 ~ 03 · 기여도 100%

상황매출처럼 자주 수정되는 ViewModel은 회귀 버그가 잦았습니다. Given-When-Then 형식의 단위 테스트 컨벤션과 이를 따르는 테스트 작성 스킬을 직접 만들어 쓰고 있었지만 커버리지를 20.6%까지 올린 뒤로는 더 높이지 못했습니다. 필요한 테스트 코드가 AI가 한 번에 다룰 수 있는 컨텍스트 양을 넘었고 생성된 테스트가 실패하면 사람이 다시 요청해 같은 작업을 반복해야 했습니다.

해결기존 테스트 작성 스킬을 바탕으로 테스트를 기능 단위로 나눠 실행하고 실패한 테스트를 고치는 단계까지 넣은 5단계 파이프라인을 Claude Code로 설계했습니다.

Planner → Scaffold → Generator → Healer → Coverage
                          ↑          ↓
                          └──────────┘  Ralph Loop: 실패 테스트 진단·수정 반복

네 번째 Healer 단계는 Claude Code의 Ralph Loop 플러그인으로 실행했습니다. 완료 조건을 통과할 때까지 같은 작업을 반복시키는 방식이라 실패한 테스트를 진단해 고치고 다시 검증하는 일을 사람이 다시 요청하지 않아도 이어 갑니다.

상담봇 RAG 설계·검증

상담봇 비용 개선 · 2026.04 ~ 05 · 기여도 100%

상황고객 상담봇은 최상위 모델이 질문마다 지식 베이스 전체를 훑어 답하는 구조라 상담 대화로 인한 토큰 사용량이 컸습니다. CX 파트에서도 토큰 부족 문제로 개선을 요청했습니다.

해결고객에게 바로 답이 나가는 시스템이라 잘못된 변경의 피해가 크다고 보고 개선안보다 평가 체계를 먼저 만들었습니다. 정답셋과 과거 상담 로그로 개선안마다 오답률, 회수율, 건당 비용을 측정해 비교했습니다.

검색은 지식 베이스 전체를 읽던 방식을 질문과 관련된 문서만 찾아 넘기는 RAG로 바꿨습니다. 원래는 Elasticsearch로 벡터 검색까지 함께 구성하려 했지만 백엔드 쪽 사정으로 쓸 수 없어 검색 파이프라인을 혼자 직접 구성했습니다. 한국어 질문은 Kiwi 형태소 분석기로 토큰을 나눠 BM25로 검색했습니다. 최종 후보는 가벼운 모델이 질문을 분류하고 이관 위험도를 먼저 표시하면 BM25로 찾은 문서 후보를 보고 답변 모델이 자동응답과 상담사 이관을 정하는 구조로 설계했습니다.

단어가 달라도 뜻이 비슷한 질문을 찾도록 bge-m3 임베딩 기반 벡터 검색을 BM25와 결합하는 안도 결합 비율과 사용 조건을 바꿔 가며 비교했습니다. 의미 매칭 자체는 좋았지만 답변 모델이 결과를 덜 확신해 상담사 이관이 늘고 비용도 올라 채택하지 않았습니다.

배포를 앞두고 지식 베이스를 감사하다가 회사 정책 문서가 별도 필터링 없이 그대로 들어가 있어 공개되면 안 되는 정보가 섞여 있는 것을 확인했습니다. 정규식과 LLM으로 만든 탐지 파이프라인으로도 일부는 찾지 못해 사람이 직접 확인해야 했습니다. 이런 데이터는 AI에만 맡기지 않고 사람이 검수해야 한다고 판단해 배포 전에 프로젝트를 멈추고 CX 파트에 검수 지원을 요청했습니다. 함께 고객 답변에 쓸 수 있는 데이터와 내부에서만 봐야 하는 데이터를 분리하는 설계를 제안했습니다.
