Keystore·AES-GCM 기반 로컬 개인정보 암호화, 강제 업데이트 없이 이관

데이터 암호화 마이그레이션 · 2025.08 · 기여도 100%

로컬 저장소에 고객 개인정보와 설정 데이터가 평문으로 남는 것을 확인하고, 배정된 업무가 아니었지만 직접 착수했습니다. DataStore에도 기본 암호화가 없어 Serializer 계층에 암호화를 넣고 Keystore에서 AES-256-GCM 키를 관리해, 쓰는 쪽 코드는 그대로 두면서 무결성 검증까지 얻었습니다. 이미 배포된 앱이라 신규 저장, 실행 시 이관, 기존 저장소 삭제의 3단계로 옮겼습니다.

결과
  • 강제 업데이트 없이 전환
  • 로그인 실패 0건

Android Keystore · AES-256-GCM · DataStore · Serializer

자세히 보기요약으로 돌아가기

상황로컬에 저장된 고객 개인정보와 설정 데이터가 평문으로 남아 있는 것을 직접 확인했습니다. 배정된 업무가 아니라 문제를 발견한 뒤 스스로 착수했습니다. SharedPreferences를 DataStore로 옮기려 했지만 DataStore도 기본 암호화를 제공하지 않아 저장 계층 자체에 암호화를 넣어야 했습니다.

해결DataStore의 Serializer 단계에 암호화 계층을 끼워 저장 시 암호화·로드 시 복호화가 자동으로 일어나게 했습니다. 쓰는 쪽 코드는 평소와 똑같습니다. 키는 Android Keystore에서 AES-256-GCM으로 생성·관리했고, AEAD를 적용해 기밀성과 무결성·변조 검증을 함께 확보했습니다. 이미 배포된 앱의 데이터라 3단계 무중단 마이그레이션으로 옮겼습니다(신규는 암호화 DataStore → 기존 SharedPreferences는 실행 시 읽어 이관 → 완료 후 삭제).

02

RemoteViews에서 Glance로 위젯 재구축, 앱과 위젯 간 데이터 불일치 해소

Compose 위젯 리뉴얼 · 2024.11 ~ 12 · 기여도 100%

앱과 위젯의 데이터가 어긋난다는 VOC가 이어졌습니다. 위젯을 Glance로 다시 만들면서 공식 문서가 부족한 부분은 라이브러리 소스를 직접 분석했고, 동기화는 WorkManager 주기 작업과 DataStore(Protobuf)로 옮겼습니다. 작업 중 절전 모드에서는 위젯 동기화가 어렵다는 것을 직접 조사해 파악했는데, 제조사마다 브로드캐스트가 달라 민감 권한을 요청하는 대신 절전 모드 해제를 안내하는 UI로 사용성을 개선했습니다.

결과
  • 데이터 불일치 VOC 해소
  • LeakCanary 도입으로 Crashlytics가 못 잡던 메모리 누수 발견
  • 운영 기간 위젯 크래시 0건(Crashlytics)

Glance · WorkManager · DataStore(Protobuf) · LeakCanary

자세히 보기요약으로 돌아가기

팀 구성 — Android 1

상황RemoteViews 기반 레거시 위젯이 유지보수가 어려웠고, 앱과 위젯 사이 데이터가 어긋나 값이 오래된 채로 남는다는 VOC, 고해상도 기기에서 텍스트가 안 읽힌다는 VOC가 들어왔습니다.

해결RemoteViews를 Jetpack Glance로 옮겼습니다. Compose 문법이지만 실제로는 RemoteViews 제약 안에서 돌아 LazyColumn 같은 기본 컴포넌트가 없고 공식 문서도 부족해, Glance 라이브러리 소스를 직접 분석하며 진행했습니다. 동기화는 WorkManager 주기 작업 + DataStore(Protobuf)로 — JSON보다 파싱 오버헤드가 적어 위젯처럼 제한된 환경에 맞다고 봤습니다. 절전 모드는 VOC로 들어온 것이 아니라 작업 중 직접 조사해 위젯 동기화가 어렵다는 것을 파악한 부분입니다. 진입 브로드캐스트가 OS·제조사(삼성/LG/샤오미)마다 달라 isPowerSaveMode()와 ACTION_POWER_SAVE_MODE_CHANGED를 조합해 감지하고, 민감 권한을 요청하는 대신 해제를 유도하는 UI로 넘겼습니다. 텍스트는 앱 실행 시 해상도·글자 크기를 저장해 렌더링 때 조정했습니다. 이 프로젝트에서 LeakCanary를 도입해 Crashlytics·ANR이 못 잡던 메모리 누수를 잡기 시작했고, 이후 실제 누수 수정으로 이어졌습니다.

결과데이터 불일치·텍스트 VOC 해소 · 절전 모드 해제 안내 UI 제공 · 운영 기간 위젯 관련 크래시 0건(Crashlytics) · LeakCanary는 이후 팀 빌드 옵션으로 정착

회고텍스트 크기 조정은 앱을 한 번 실행해야 반영됩니다. 위젯 단독으로 갱신할 방법을 못 찾았고, 그 한계는 그대로 남았습니다.

Java·MVC 레거시를 Kotlin, 모노레포, MVI, Compose 순으로 무중단 전환

레거시 아키텍처 전환 · 2021.11 ~ 2025 · 기여도 30~100%

Java 71%에 MVC와 AsyncTask로 된 코드였고 서비스는 멈출 수 없었습니다. 영향도가 낮은 파일부터 Kotlin으로 옮기고, 앱별로 나뉜 레포를 3-Layer 멀티모듈 모노레포로 합쳤습니다. MVI는 구조를 깊이 이해하고 싶어 하던 팀원과 함께, Now in Android처럼 외부 의존성 없이 자체 코드로 만들어 보자는 챌린지로 시작해 Orbit 코드를 분석하며 같이 학습하고 구현했습니다. Compose·MVI 스터디도 열어 Android 구성원과 함께 옮겼습니다. 전환 뒤 병목이던 빌드는 kapt보다 빠른 KSP로 바꾸면서 Kotlin 2.0(K2 컴파일러) 업그레이드와 병렬 빌드·캐시 활성화를 한 PR로 처리했습니다.

결과
  • Kotlin 비율 28.8% → 99.2%
  • 3개 앱을 단일 모노레포로 운영
  • 빌드 최대 8분 → 3분

Kotlin · Compose · MVI · Flow · 멀티모듈 · 모노레포 · Gradle Kotlin DSL · KSP · 빌드 캐시

자세히 보기요약으로 돌아가기

팀 구성 — Android 3

상황Java 71%의 MVC + AsyncTask 레거시. 앱마다 레포가 나뉘어 있어 공통 코드가 중복됐습니다. 서비스는 계속 굴러가야 했으므로 한 번에 갈아엎는 선택지는 없었습니다.

해결서비스를 멈추지 않으려고 축을 4개로 나눠 순차 전환했습니다(Kotlin → 모노레포 → MVI → Compose).

단계 전환 판단
1 Java → Kotlin 신규 프로젝트는 Kotlin으로 시작, 레거시는 영향도가 낮은 파일부터 높은 순으로 전환
2 멀티레포 → 모노레포 Presentation / Network / Common 3-Layer 멀티모듈 (Android 3인 협업)
3 MVVM → MVI MVI를 깊이 이해하고 싶어 하던 팀원과, Now in Android처럼 외부 의존성 없이 자체 코드로 만들어 보자는 챌린지로 시작 — Orbit 코드를 분석하며 함께 학습하고 reduceState + postSideEffect 두 축으로 직접 제작
4 DataBinding → Compose 종료 예고를 보고 선제 전환 — 분산된 상태를 ViewModel 중심으로 통합

함께 넘어가기 위해 Compose/MVI 팀 스터디를 주최하고 코드 컨벤션을 같이 다듬었습니다.

결과
- Java → Kotlin 28.8% → 99.2%
- Compose + MVI 전환 후 동일 유형 작업의 예상 스토리포인트 20% 감소(스프린트 작업 티켓 기준)
- 앱별 레포를 모노레포로 통합 → 3개 앱 단일 구조 운영
- OS 17 회전 디바이스 확장에 별도 대응 없이 자동 호환

미리 옮겨둔 효과는 나중에 드러났습니다.

전환 뒤 빌드 최적화 | 2025.01 | 기여도 100%

상황아키텍처를 옮기고 나니 다음 병목이 빌드였습니다. 구버전 AGP로 최대 8분이 걸렸고, 병렬 빌드와 캐시가 모두 꺼져 있어 증분 효과도 거의 없는 상태였습니다.

해결두 단계로 나눠 진행했습니다. 먼저 VersionCatalog 도입으로 모듈 간 버전 불일치를 없앴습니다.

이어서 kapt를 KSP로 전환하고 Kotlin 2.0으로 올렸습니다. kapt는 어노테이션 처리를 위해 Java 스텁을 먼저 만들어야 해서 느리고 유지보수 모드에 들어간 도구인 반면, KSP는 Kotlin 코드를 직접 읽어 스텁 단계가 없습니다. Kotlin 2.0의 K2 컴파일러는 컴파일 속도 자체가 빨라졌지만, kapt와 함께 쓰면 이전 컴파일러 방식으로 되돌아가 그 이점을 얻을 수 없습니다. 두 가지가 서로 맞물려 있어 KSP 전환과 Kotlin 2.0 업그레이드를 한 작업으로 묶어 빌드 속도를 함께 끌어올렸습니다. 같은 PR에서 AGP·Gradle 최신화, groovy → Kotlin DSL, 병렬 빌드·캐시 활성화까지 함께 처리했습니다.

결과
- 빌드 최대 8분 → 3분

이후에도 Gradle 빌드 추가 최적화와 Kotlin 데몬 메모리 분리(컴파일 OOM 방지)를 이어갔습니다.

AI 기반 ViewModel 테스트 자동 생성 파이프라인 설계, 커버리지 20.6% → 83%

테스트 자동화 · 2025.07 ~ 2026.02 · 기여도 100%

기존 생성 스킬로는 3,805줄짜리 매출 ViewModel이 컨텍스트 한계에 걸려 LINE 커버리지 20.6%에서 멈췄습니다. 계획·골격·생성·커버리지 측정 사이에 실패한 테스트를 스스로 진단해 고치는 단계를 둔 파이프라인을 Claude Code로 설계하고, 분기를 타지 못하던 relaxed mock은 MockWebServer와 JSON fixture로 바꿨습니다.

결과
  • 3,805줄 ViewModel 기준 LINE 20.6% → 83%
  • BRANCH 6.3% → 52%
  • 이후 전체 ViewModel에 적용

Claude Code · JUnit5 · Turbine · MockK · JaCoCo

자세히 보기요약으로 돌아가기

상황기존 자동 생성 스킬이 LINE 커버리지를 20.6%까지 올려둔 상태였는데, 생성된 테스트가 실패하면 결국 사람이 붙어야 해서 그 위로 올라가지 못하고 있었습니다.

자동화에 앞서 테스트를 어떤 모양으로 쓸지부터 정했습니다. Given-When-Then 패턴을 표준으로 잡아 요구사항 단위로 시나리오를 설계했고, 대상은 ViewModel의 비즈니스 로직으로 한정했고(JUnit5 · MockK · Turbine), UI 테스트는 이 파이프라인의 범위에 넣지 않았습니다. 형식이 정해져 있어야 자동 생성이 의미를 갖는다고 봤기 때문입니다.

해결생성만으로는 부족하다고 보고, 고치는 단계까지 넣은 5단계 파이프라인을 Claude Code로 설계했습니다.

Planner → Scaffold → Generator → Healer → Coverage
                          ↑          ↓
                          └──────────┘  실패 테스트 자동 진단·수정 루프

핵심은 네 번째 수정 단계(Healer) 입니다. 실패한 테스트를 자동 진단해 고치고 다시 검증 루프를 도는 구조라, 사람 개입 없이 통과 가능한 지점까지 도달합니다.

결과
- 3,805줄 ViewModel 기준 LINE 20.6% → 83% / BRANCH 6.3% → 52% / METHOD 30% → 88% — 이후 전체 ViewModel에 적용
- QA 집계 기준 회귀 버그 티켓 50% 감소

세 지표를 함께 보는 이유는 LINE만으로는 분기 미탐지가 가려지기 때문입니다.

회고초기에 relaxed mock을 쓰다 분기를 못 잡는 문제가 있었습니다. MockWebServer + JSON fixture 패턴으로 전환했습니다.

배포 장애를 계기로 RemoteConfig 피처 플래그를 제안·도입하고 정기 배포로 전환

통합 회원가입 · 2021.11 ~ 2022.03 · 기여도 100%

원장·직원 회원가입 통합을 배포한 뒤 백엔드 장애가 났는데, 네이티브 앱은 심사와 배포를 거쳐야 해서 빠르게 대응하기 어려웠습니다. 이후 Firebase RemoteConfig 피처 플래그 도입을 제안해 배포 없이 기능을 켜고 끌 수 있게 했고, 불규칙하던 배포는 정기 배포로 바꿨습니다.

결과
  • 통합 회원가입 배포
  • 피처 플래그는 이후 큰 프로젝트 배포에서 활용
  • 정기 배포로 전환

상황원장과 직원의 회원가입이 분리돼 있었습니다. VOC·버그 대응으로 주 2~3회 불규칙하게 배포하던 상황이었습니다.

해결회원가입을 통합하고 강제/선택 업데이트를 구현했습니다. 배포 후 백엔드 롤백이 필요한 크리티컬 이슈가 났는데, 네이티브 앱은 심사와 배포를 거쳐야 해서 기민하게 대응하기 어려웠습니다. 그래서 Firebase RemoteConfig 피처 플래그 도입을 제안해 배포 없이 기능을 켜고 끌 수 있게 했고, 불규칙 배포를 정기 배포로 바꿨습니다. 업무 우선순위 제도도 함께 도입했습니다.

결과통합 회원가입 배포. 이후 장애는 앱 배포 없이 피처 플래그로 기능을 내려 대응할 수 있게 됐고, 이후 큰 프로젝트 배포에서 활용했습니다

회고백엔드는 바로 되돌릴 수 있어도 네이티브 앱은 장애에 기민하게 대응하기 어렵다는 것을 겪었습니다. 정기 배포와 피처 플래그가 왜 필요한지 이때 체감했습니다.
